# ICMS 智慧教室管理系统需求设计文档

## 1. 引言

### 1.1 项目名称

智慧教室管理系统（ICMS，Intelligent Classroom Management System）

### 1.2 技术栈

- 后端：Spring Boot、Spring Security / JWT、MyBatis-Plus 或 MyBatis、Maven
- 数据库：MySQL 8.x
- 前端：Vue 3、Vue Router、Pinia、Axios、Element Plus、ECharts
- 部署：Nginx、JDK 17、Docker（可选）

### 1.3 编写目的

本文档用于说明 ICMS 系统的业务背景、功能需求、非功能需求、系统架构、核心流程和接口设计方向，为后续数据库设计、后端开发、前端开发、测试验收和项目答辩提供依据。

## 2. 项目背景

在高校和培训机构中，教室数量多、设备类型复杂、使用人员多样，传统人工管理方式容易出现以下问题：

- 教室预约依赖线下登记，效率低。
- 教室使用状态不透明，容易出现占用冲突。
- 设备故障反馈链路长，维修进度难追踪。
- 教室环境数据缺乏统一监控。
- 管理人员难以及时统计资源利用情况。

ICMS 通过信息化方式统一管理教室、设备、课表、预约、工单和环境数据，形成「资源维护—状态查询—预约审批—使用反馈—统计分析」的闭环。

## 3. 建设目标

| 目标 | 说明 |
|---|---|
| 资源数字化 | 将校区、楼栋、教室、设备等基础数据统一建档 |
| 流程在线化 | 教室预约、审批、报修、维修处理全部线上完成 |
| 状态透明化 | 用户可实时查询教室占用、设备状态和环境信息 |
| 管理精细化 | 支持按照校区、楼栋、时间段统计教室使用率 |
| 权限规范化 | 基于角色控制菜单、按钮和数据访问权限 |

## 4. 系统边界

### 4.1 系统包含

- 用户登录与认证授权
- 用户、角色、权限管理
- 校区、楼栋、教室管理
- 设备资产管理
- 课程排课与教室占用
- 教室预约申请与审批
- 报修与维修工单
- 环境监测数据管理
- 通知公告
- 统计分析
- 操作日志

### 4.2 系统暂不包含

- 真实硬件门禁控制的底层驱动开发
- 实时视频监控流媒体服务
- 第三方教务系统深度双向同步
- 复杂AI预测算法

以上内容可作为后续扩展模块。

## 5. 用户角色与权限需求

| 角色 | 权限范围 |
|---|---|
| 系统管理员 | 系统全部配置、用户角色权限、日志审计 |
| 教务管理员 | 教室、课表、预约审批、统计分析 |
| 教师 | 个人课表、教室查询、预约申请、报修申请 |
| 学生 | 空闲教室查询、预约申请、公告查看 |
| 维修人员 | 查看和处理分配给自己的维修工单 |

权限控制要求：

- 前端根据权限动态生成菜单。
- 后端接口必须进行权限校验，不能只依赖前端隐藏按钮。
- 用户禁用后不得继续访问系统。
- 删除业务数据建议采用逻辑删除。

## 7. 非功能性需求

| 类型 | 需求说明 |
|---|---|
| 性能需求 | 普通查询接口响应时间建议小于 1 秒；复杂统计接口建议小于 3 秒 |
| 安全需求 | 密码必须加密存储，接口必须鉴权，重要操作记录日志 |
| 可用性需求 | 页面交互清晰，表单校验友好，错误信息可理解 |
| 可维护性需求 | 后端分层清晰，前端组件化，接口命名规范 |
| 可扩展性需求 | 后续可扩展门禁控制、IoT设备接入、大屏展示 |
| 兼容性需求 | 支持主流浏览器，如 Chrome、Edge、Firefox |
| 数据一致性 | 预约和排课必须进行事务控制，避免并发冲突 |

## 9. 核心业务流程

### 9.1 教室预约流程

```text
用户选择日期和节次
        ↓
系统查询空闲教室
        ↓
用户提交预约申请
        ↓
系统进行课程和预约冲突检测
        ↓
生成待审批预约记录
        ↓
管理员审批
        ↓
通过：教室时间段被占用
驳回：用户可查看驳回原因
```

### 9.2 工单处理流程

```text
用户提交故障报修
        ↓
系统生成工单
        ↓
管理员分派维修人员
        ↓
维修人员处理
        ↓
填写处理结果
        ↓
工单关闭并归档
```

## 10. 接口设计示例

| 模块 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 登录 | POST | `/api/auth/login` | 用户登录 |
| 用户 | GET | `/api/users` | 用户分页查询 |
| 教室 | GET | `/api/classrooms` | 教室分页查询 |
| 教室 | POST | `/api/classrooms` | 新增教室 |
| 空闲查询 | GET | `/api/classrooms/free` | 查询空闲教室 |
| 预约 | POST | `/api/reservations` | 提交预约申请 |
| 预约 | POST | `/api/reservations/{id}/approve` | 审批预约 |
| 设备 | GET | `/api/devices` | 设备查询 |
| 工单 | POST | `/api/work-orders` | 提交报修 |
| 工单 | POST | `/api/work-orders/{id}/handle` | 处理工单 |
| 环境 | GET | `/api/environment/records` | 环境数据查询 |

## 11. 数据校验规则

| 对象 | 字段 | 规则 |
|---|---|---|
| 用户 | username | 必填，唯一，长度 4-50 |
| 用户 | password | 必填，加密存储，不明文返回 |
| 教室 | room_no | 同一楼栋下唯一 |
| 教室 | capacity | 必须大于 0 |
| 设备 | device_code | 全局唯一 |
| 预约 | start_section / end_section | 开始节次小于等于结束节次 |
| 预约 | attendee_count | 不能超过教室容量 |
| 工单 | fault_title | 必填，长度不超过100 |

## 12. 验收标准

- 用户能够完成登录、退出、权限菜单加载。
- 管理员能够维护教室、设备、课表等基础数据。
- 用户能够查询空闲教室并提交预约申请。
- 系统能够阻止课程或预约时间冲突。
- 管理员能够审批预约并记录审批意见。
- 用户能够提交报修，维修人员能够处理工单。
- 系统能够展示统计图表和基础日志。
- 数据库表结构完整，核心字段满足业务需要。
